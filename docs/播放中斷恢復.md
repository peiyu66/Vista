# 播放中斷恢復

2026-11-07。Build66 已由使用者在實機確認：摘下再戴上後保持暫停，手動播放正常；離開影片、切換其他影片及切換目錄正常。本文件是正式採用的 renderer 與 SMB 播放來源恢復規格。來源基底、測試計數與仍未驗項目統一見 [已驗收基底](已驗收基底.md)，匿名事件見 [生命週期診斷](生命週期診斷.md)。

## 兩層恢復與暫停意圖

Build65 加入 renderer 恢復，Build66 在其上補上 byte-source 恢復；本次以 Build66 的完整組合接受，不把兩層視為分別完成實機驗收。

- **Renderer：** `VideoRendererRecoveryGate` 與 `SystemVideoPresenter` 只處理明確的 `requiresFlushToResumeDecoding`。保留單一 pending frame、retained frame、序列 flush／enqueue 及 generation 防護；同一影片 session 的一次前景區間最多嘗試一次恢復。真正 scene 中斷才更新預算，正常影格或重複通知不補充預算。
- **播放來源：** `PlaybackRecoveringSource` 在合格 SMB 讀取失敗傳給 AVPlayer 前，先退役並排空舊來源，再建立一次新連線、核對檔案觀測身分及重讀同一 range。它不重建播放時鐘、不將位置歸零，也不以舊影格掩蓋已停止的播放。
- **Scene 與使用者意圖：** 只在 background 呼叫原有暫停。inactive 通知 renderer 停止呈現並更新來源 gate，不提早 pause；回 active 不自動播放。renderer 恢復前要求同一有效 session 的上游暫停，與 inactive 提早 pause 是不同流程。已停止、失敗或過期的 session 不得藉恢復重新出現。

來源 gate 由實際 immersive scene 同步，包含 onAppear 與新來源綁定；不以 browser 視窗 background 誤判播放狀態。scenePhase 是系統／視窗事件，不是摘戴感測器。

## 每片來源、所有權與清理

每次選片、重試、上一部／下一部及停止後重播，都建立綁定固定 `MediaFile` 的新 wrapper。檔頭、格式 metadata 與真正播放共用同一份，不沿用已取消或屬於前一影片的來源。

初始 provider 借自瀏覽 session。正常停止不 disconnect 健康的借用來源；合格失效時才停止舊 provider 的新工作入場，等待實際 lease 及 library callback queue 排空，完成本地退役後才建立 fresh provider。Task 取消、continuation 返回或計時器到期均不代表底層排空。

恢復建立的 provider 是 wrapper 私有，不發布至目錄 registry；停止或換片時清理自己擁有的來源。`PlaybackController.awaitPreparedSourceCleanup()` 在同一 controller 下一次來源 factory 與 metadata 開始前，等待先前已啟動的實際清理。清理失敗保持阻擋並顯示固定錯誤，不以新連線繞過。已啟動的退役即使原請求取消仍須善後；本項測試不代表跨畫面重建的所有時序均已覆蓋。

## 一次重試、需求與前景預算

同一失效 provider 共用一個恢復 episode；每個原始 metadata／range 請求最多使用一次恢復，不遞迴重試 fresh read 的失敗。同一 episode 最多一次 fresh connect，舊回呼不得撤銷或取代新 session。之後獨立請求若遇到下一次真正失效，才有自己的有界 episode。

- 背景失敗只等待 active 或取消，不背景重連、不輪詢保活。
- 單一 ResourceBridge read 因 seek 等原因取消，只退出該 waiter，不取消其他仍有需求的 waiter。
- 最後一個 waiter 取消後，未完成 episode 等待下一個需求或整體停止；新需求不被誤判為永久取消，既有一次連線預算不重設。
- 沒有 live demand 或來源已停止時，不新建連線、重試或交付 bytes。每個 await 後重新核對取消、generation、來源及帳號設定仍是目前選擇。
- 僅同一舊 slot 的晚到成功回呼，或來自同一舊 slot 的 typed `.retired`，可加入既有 episode；普通 `.retired` 不能自行啟動新 episode，也不因此忽略真正權限錯誤。

`NativePlaybackSession` 的原有 15 秒無進展判斷，在明確來源恢復期間提供最多累計 **45 秒 active grace**。inactive／background 與沒有 live demand 的等待不計入，但也不重設已消耗時間；需求恢復後續計原額度。額度耗盡後禁止新的 publication／retry，已啟動的清理仍必須完成。

45 秒是來源恢復的 active 額度，不是 transport 的硬牆鐘 timeout。SMB 原 15 秒設定、poll 與 manager queue 都不變；OS 排程、鎖及已開始的 callback 實際完成時間沒有因此取得硬上限。

## 播放專用錯誤與檔案觀測身分

`SMBPlaybackSession` 使用播放專用 typed 介面，保留失敗來源，不將所有錯誤洗成 unavailable。只有 `serviceInvalidated`、`contextUnavailable`、已識別的 transport failure，以及成功由播放恢復退役的來源可進 fresh recovery。未分類錯誤、普通 retired、取消、真正權限／認證／不存在、短讀、超長回覆、無效 range 及身分變動不自動重試。這比目錄唯讀重列的允許分類更窄。

首次 stat 保存 size、mtime、btime、ctime，以及可用非零 inode／documentIdentifier，只留記憶體、不寫診斷。首次缺少身分欄位仍可正常播放，但跨新 session 續接須有有效 mtime／btime，並比對 size 及所有可選 ctime／非零識別欄位；原欄位消失或改變均拒絕，不降級忽略。初始 metadata 尚未取得、且未交付 bytes 時，合格失效可經一次新連線建立第一個 baseline。

新來源重讀前與交付前再次核對觀測身分；重讀沿用原 64-bit range，回傳長度須精確相同。metadata 指紋不是持續開檔的 SMB FileId 或不可變 snapshot，即使相符仍可能漏掉保留相同 metadata 的內容變化。無法確認續接身分時明確失敗，不宣稱完整一致性。

## 與目錄恢復及既有依賴的分工

[DirectoryReadRecovery](../Sources/VistaCore/DirectoryReadRecovery.swift) runner 不變。一般失效仍要求 playback 已結束，目錄不能撤銷播放器仍借用的 provider。唯一例外是 `retiredByPlaybackRecovery`：必須由播放專用退役完成實際排空後才標記；此時舊來源已排空且不再接受播放讀取，播放恢復另行建立私有來源，目錄可獨立透過原 runner 接手上一部／下一部補頁。marker 不代表 fresh 連線已成功或發布。registry、generation 與 provider 身分檢查繼續保留，普通 retired 或失敗清理不取得此例外。

AMSMB2／libsmb2 上游來源、兩份 patch、SO_NOSIGPIPE、既有 callback／handle 防護、timeout 及 queue 均沿用已接受基底，沒有新增底層連線策略。依賴及目錄策略的唯一正式來源仍是 [SMB 目錄恢復](SMB目錄恢復.md)。本次不接入 MKV 的 `SMBReadSession`／Admission 研究，也不恢復先前的多請求併發驗證。

## 驗收界線

本次接受的是使用者實測的摘戴後手動播放、離開影片、換片及切目錄情境；未另確認重戴後尚未按播放前的靜止影格是否可見。來源、renderer 與匿名診斷的本機測試及合成 UI 另列於 [已驗收基底](已驗收基底.md)，不與使用者觀察重複計數。

AVPlayer 已進 failed、檔案身分不足或改變、重試仍失敗、清理未完成等情況仍可明確失敗。沒有宣稱所有摘戴、網路、退出或 GPU／雙眼光學情境均解決；3× 卡頓、部分跳轉等待、完整 VP9／MKV／HDR 與長時表現仍保留原限制。無匹配終止證據的回 Home 事件維持停止追查，不藉本次結案推定根因。
