# 開發與測試

2026-11-03 初期原型。最低目標 visionOS 2；本輪使用 Xcode 27.1（27A9275）、Swift 6.4、visionOS 27 SDK 與 visionOS 26.1 模擬器。只有模擬器與核心測試，沒有實機測試或上架。

## 建置

開啟 `Vista.xcodeproj`，選擇 Vista scheme 與 Vision Pro Simulator。首次解析固定版本 AMSMB2 4.0.3，需要網路。不要選實體裝置；簽署與實機操作未包含在本輪測試。

```sh
swift test --no-parallel
xcodebuild -project Vista.xcodeproj -scheme Vista \
  -sdk xrsimulator -destination 'generic/platform=visionOS Simulator' \
  -derivedDataPath /tmp/VistaDerivedData CODE_SIGNING_ALLOWED=NO build
```

UI 測試請選擇已建立的 Vista 專用模擬器，執行 Product → Test。命令列可用 `-destination 'platform=visionOS Simulator,id=<該裝置 UUID>' test`。不要把私人伺服器、帳密或媒體放進測試參數／Git。

## 程式分工

- `Sources/VistaCore/Browser.swift`：固定兩欄導覽、快取、選取、捲動位置、載入、取消與過期回應防護；純人工資料 provider 與連線欄位驗證。
- `Sources/VistaCore/MediaInspection.swift`：檔案識別驗證、有界檔頭來源與初步辨識，不推定解碼支援。
- `Sources/VistaSMB/SMBDirectoryProvider.swift`：AMSMB2 session、連線／唯讀列目錄／有限量檔頭／離開時斷線；15 秒操作 timeout；不公開底層錯誤。
- `VistaApp/VistaApp.swift`：SMB 連線表單、兩欄介面、同視窗播放預覽。示範資料入口明示其為人工資料。
- `Tests/VistaCoreTests`：根層、深入／返回／同層切換、取消競態、錯誤、5,000 筆、路徑與重複 ID 過濾、播放返回、欄位驗證。
- `VistaUITests`：在 visionOS 模擬器操作連線頁、兩欄、播放入口及返回。

## 已採用的互動

永遠維持兩個欄位位置。右欄是目前目錄，左欄是其父目錄內容。右欄點子目錄後兩欄向下一層移動；返回讓父目錄成為右欄。左欄點其他資料夾切換右欄；不增加第三欄。分享根目錄顯示實際分享名稱，返回停用；不額外顯示「已在最上層」或底部操作教學。

瀏覽標題分為「伺服器：主機名稱或 IP」、「分享：分享名稱」及目前分享內路徑。伺服器與分享名稱取自成功連線時提交的快照，不從仍可編輯的表單讀取，避免連線等待期間改字造成標題與 session 不符。若使用主機名稱連線，顯示該名稱；若只知道 IP，原樣顯示 IP（含 loopback），不假稱已取得遠端電腦名稱。不額外進行反向 DNS、Bonjour 或 NetBIOS 探測，避免名稱查詢阻擋連線；目前未取得 SMB 伺服器回報的顯示名稱。分享名稱不是伺服器名稱，兩者分行並獨立截斷長文字。

每個已走訪目錄保留已載入項目、選中項目及捲動 ID。播放在同一視窗覆蓋顯示，暫時隱藏瀏覽內容，不重新建立瀏覽模型。快速切換以取消工作及 generation token 拒絕過期結果；取消不代表底層網路 I/O 已立刻停止。

連線按鈕與密碼欄 Return 共用送出動作，無效欄位顯示說明，連線中顯示進度並防止重複送出。空資料夾、載入中、失敗／重試均有獨立狀態。檔案不能改名、移動、複製、刪除，不提供本機來源。非影片檔案停用；副檔名只是播放入口分類，不是解碼支援判定。

## 隱藏項目

檔案與資料夾同樣處理：名稱以 `.` 開頭（含 `.DS_Store`、`.DS_STORE`、`._` 與點開頭資料夾）不顯示；若回傳 `.isHiddenKey == true` 亦不顯示。普通名稱中間的點號不受影響，隱藏屬性缺少時保留為未知，不當作 hidden。SMB adapter 在排序／分頁前過濾，瀏覽模型也套用相同規則，避免其他來源漏入；隱藏項目不列入顯示數量且不能選取。

已查核 AMSMB2 4.0.3 的 `listDirectory` 與 `smb2_stat_64.populateResourceValue`：目前列舉回傳沒有 `.isHiddenKey`。因此現有真 SMB 路徑可確實執行點開頭規則；非點開頭的 SMB hidden flag 支援已接妥並以人工 metadata 測試，但受上游未提供屬性限制，不能宣稱目前都能辨識。沒有逐檔額外查詢、修改屬性或模擬完整 Finder 隱藏規則。

## 憑證與 SMB

伺服器目前接受主機名稱或 IPv4（標準 445 埠），分享名稱另填；不接受內嵌帳密 URL、IPv6、非標準埠。使用者名稱／SecureField 指定系統語意；沒有 Associated Domains，也未實測 Apple 密碼配對。連線後清空密碼欄位，AMSMB2 僅在 session 記憶體保有憑證；不做 Keychain、偏好或檔案儲存，不記錄密碼。Swift 字串不宣稱可保證零化。

保留 AMSMB2/libsmb2 的協商與簽章設定，並依伺服器要求啟用 session/share encryption；不做匿名退回或 SMB1 降級。已完成一次從模擬器登入既有 Mac 分享及根目錄列舉；SMB2／SMB3 方言、簽章、加密及 Tailscale 均仍需實際協商驗證。

套件 `contentsOfDirectory` **先完整讀取目錄**，再由 adapter 排序並每 100 筆提供給 UI；這不是網路端增量列舉。adapter 最多保留 8 個目錄快取；瀏覽模型保存本次走訪狀態。大量目錄延遲、峰值記憶體與網路分頁仍未驗收，後續應評估串流列舉 API 及快取淘汰策略，不能把人工資料 5,000 筆測試當成真 SMB 效能。

## 媒體資訊準備階段

`MediaInspection.swift` 定義分享內檔案識別、檔頭來源與辨識結果。進入預覽後，SMB adapter 查詢檔案型別／大小，只對一般檔案讀取開頭最多 65,536 bytes，不下載整支影片、不寫入磁碟。顯示檔案大小及初步檔頭類型；讀取失敗只給通用錯誤與重試，返回會取消 UI 工作並拒絕遲到結果。既有第三方單次 I/O 不保證立即中止，仍受 15 秒 timeout 約束；這不是可 seek 的影片串流器。

目前只辨識完整的開頭 `ftyp` box（ISO BMFF 家族、QuickTime major brand）及 EBML magic；EBML 不能直接當成 Matroska，未知／截斷／其他排列保留「尚未辨識」。這一層不解析軌道，也不把檔頭當成可播放證明；按播放後改由系統解析軌道、codec、時長與畫面尺寸。人工示範來源明示「示範資料」，使用專案自造的 64 × 64、24 幀、2 秒灰階影片。

真實 SMB 的檔案內容讀取本輪未重播，原已登入 app 不更新、不讀取私人影片。使用者日後在新版選片後會讀取檔頭，按播放才啟動完整軌道解析與串流讀取。

格式邊界參考 [W3C ISO BMFF byte stream](https://www.w3.org/TR/mse-byte-stream-format-isobmff/) 與 [Matroska EBML 約束](https://www.matroska.org/technical/basics.html)。硬體解碼限定不變，沒有加入 AVPlayer、軟體解碼或轉碼。

## 硬解限定視訊原型

`Sources/VistaMedia/HardwarePlayback.swift` 使用 `AVURLAsset`／`AVAssetResourceLoader` 解析 MP4、M4V、MOV 的單一視訊軌道。SMB session 透過 `MediaByteSource` 提供檔案大小及有界 range 讀取；送給 AVFoundation 的 URL 只有 opaque session 路徑，不含伺服器、帳號、密碼或私人檔名。loader 每次取 64 KiB、最多 8 個並行要求；SMB adapter 單次最多 1 MiB，不寫影片磁碟快取。AVFoundation 若要求讀至 EOF，目前仍按要求連續回傳分塊，尚無依播放位置限制預取的機制；64 KiB 是單次讀取上限，不是總預取量保證。AVFoundation 內部快取、真實大影片的網路預取與效能尚未量測。

`AVAssetReaderTrackOutput(outputSettings: nil)` 只提供原始壓縮樣本，解碼交給 VideoToolbox。辨識 H.264、HEVC、VP9 後，必須以 `RequireHardwareAcceleratedVideoDecoder = true` 建立 session，且查詢 `UsingHardwareAcceleratedVideoDecoder == true` 才接受影格；每批解碼後再次確認。建立失敗、查詢失敗或非硬解，一律顯示不能確認硬解並停止，沒有軟解分支。格式變更、多視訊軌道、保護內容、未知 codec 或系統無法解析的容器會明確失敗；目前 MKV 未接入，不能因列出 VP9／HEVC 辨識分支就宣稱已相容。

解碼後使用 CoreImage 處理方向及產生顯示影格，這是已解碼像素的呈現，不是軟體影片解碼。依 CoreMedia 輸出時間戳處理 edit list 與 B-frame 排序，循序依時鐘顯示；自有待顯示佇列上限 32 幀／128 MiB，超限或異常時間戳停止。這是平面視訊原型，尚非高解析度 VR renderer，效能與色彩／HDR 尚未驗收。播放完保留末幀；停止或返回取消工作、清除畫面，遲到回應不覆蓋新工作。底層單次 SMB I/O 仍可能等至 timeout 才結束。

沒有音軌時 UI 顯示「影片無音軌」；目前從頭播放，支援暫停／繼續、停止、位置跳轉及返回；時間列可拖曳。下一階段需在另獲授權後進行 Vision Pro 的硬解與真 SMB 影片讀取驗證，並驗證音畫同步、跳轉效能、VR 呈現及格式矩陣；不可把 Mac 測試當成裝置驗收。

專案自造樣本為 `Sources/VistaCore/Resources/Synthetic.mp4`（2,058 bytes；SHA-256 `4f09dbc543fceeb4c8db615045ac0d2c65d5d720d594471156f07904cbd3e01d`），來源程式為 `tools/GenerateSyntheticMovie.swift`，可自行重製，沒有外部影片或再散布授權依賴。編碼器版本可能讓重製位元組不同。gitignore 僅例外允許此固定樣本及下述自造音畫／跳轉測試樣本，其餘影片仍忽略。

官方依據：[壓縮軌道輸出](https://developer.apple.com/documentation/avfoundation/avassetreadertrackoutput/init(track:outputsettings:))、[要求硬體解碼](https://developer.apple.com/documentation/videotoolbox/kvtvideodecoderspecification_requirehardwareacceleratedvideodecoder)。同時核對本機 visionOS 27 SDK 的 VideoToolbox／CoreMedia headers，保留最低 visionOS 2 相容 API。

## SMB 可定位讀取邊界（2026-11-03）

正式路徑為 `SMBDirectoryProvider → SMBMediaReader → AMSMBRangeTransport → AMSMB2`。獨立的 `SMBRangeTransport` 僅作內部測試替身入口；產品連線仍使用原認證 manager，不增加帳號、分享或測試服務。`SMBMediaReader` 統一檔案型別／大小驗證、64-bit offset、1 MiB 單次上限、空範圍不做 I/O、短讀／超量回應拒絕、錯誤清理及關閉／取消後丟棄遲到資料。

`MediaReadPlan` 針對 AVFoundation 的 requested/current offset、長度、EOF 要求驗證範圍，以惰性 iterator 產生最多 64 KiB 的連續 chunk，不預先建立大檔案的所有請求陣列。resource loader 每次回傳 chunk 後讓出執行權，讓取消／重新定位回呼能處理，再發出下一次讀取。

可控測試把專案自造影片的 moov 索引移到 16 MiB 及 4 GiB 的虛擬空白區之後；沒有建立大型檔案或網路分享。經正式 SMBMediaReader 邏輯接至系統容器解析及硬解路徑，驗證可以跳過空白區取得檔尾索引。確切讀取量與硬解結果見驗收文件；此替身不是 SMB 協定伺服器，不能證明實際網路連線或延遲表現。

目前 AMSMB2 每次 range 呼叫重新開檔，沒有跨多次 range 的固定檔案 handle 或版本快照。截短造成短讀會失敗，但同大小替換或讀取中變動不保證可偵測；後續真 SMB 測試需使用不變的合成檔案，並驗證斷線、延遲、重新開檔成本及大檔預取。64 KiB 仍只是單次上限，不是對所有容器的總讀取量保證。

已在受控的本機 SMB 測試環境完成合成小檔範圍讀取與 SHA-256 比對，測試檔已核對並移除。這不代表跨機網路、大影片或裝置播放成功；詳細證據見驗收文件。現有硬解限定不變，Vision Pro 操作仍需另行許可。

## 播放時間控制

無音軌時，`PlaybackTimeline` 以單一播放工作專用的單調時鐘排程影格，扣除暫停期間；暫停與影格交付在 MainActor 序列執行，避免按下暫停後仍更新可見影格。繼續時重算排程期限，不以補播方式追趕暫停時間。暫停等待可被取消，停止或返回沿用既有取消及過期回應防護。

畫面提供「暫停／繼續」、目前時間／總時長與可拖曳的時間列；進度依已交付影格時間更新，完成時到達總時長，停止時歸零。暫停會阻止下一次壓縮樣本要求與可見影格前進，但不承諾立即停止既有 SMB I/O 或 AVFoundation 預取。VR 呈現目前為下述原型；Mac 的時間控制測試不替代 Vision Pro 互動驗收。

## 基本音訊與音畫共同時鐘

單一 AAC／PCM 音軌先限定 1–2 聲道、8–48 kHz；多音軌、不支援格式或中途格式變化會停止，不默默丟棄聲音。`AudioPlayback` 用獨立 AVAssetReader 將音訊解成 16-bit interleaved PCM，交給系統 `AVSampleBufferAudioRenderer`。這是音訊解碼；影片依然只使用通過屬性驗證的 VideoToolbox 硬解 session，硬解未成立前不建立音訊播放工作。

有音軌時，影格跟隨 `AVSampleBufferRenderSynchronizer` 的音訊輸出時鐘，不再各自跑兩個時鐘。排程等待期間持續補給音訊，因此影格稀疏時也不只在下一幀才補音訊。音訊以目前時鐘最多預取約 0.5 秒，加一個待送 packet；每個 PCM packet 限 0.25 秒／192,000 bytes，尊重 renderer ready 狀態。此上限不涵蓋 AVFoundation 內部快取或 SMB 原始資料預取。

暫停／繼續調整同一音訊時鐘速率；停止及返回立即停止、清空 renderer，再取消讀取。最後影格後仍等待音訊時間到達媒體結尾。音訊錯誤、輸出自動 flush／重新配置或 visionOS audio session interruption 採停止，不自動重建；時鐘無進展超過 3 秒，或影片落後音訊達 0.5 秒亦失敗停止。這是初期錯誤界線，不是已驗證的同步精度保證，慢網路仍需後續緩衝策略。

visionOS 使用 playback／moviePlayback audio session，結束時解除 active。實機輸出、耳機／喇叭延遲、路由切換及中斷尚未驗收；未承諾多聲道、空間音訊、背景播放或精準唇音同步。最低 visionOS 2 相容 API 在新版 SDK 有棄用提示，仍可建置；未改用僅新版可用的 receiver API。

自造音畫樣本 `Tests/VistaCoreTests/Resources/SyntheticAV.mp4` 為 2 秒 H.264 灰階畫面＋48 kHz 單聲道 AAC 440 Hz 低振幅音，僅套件測試使用；產生器加 `--audio` 可重製。自動測試將 renderer 靜音，確認解碼、交付與時鐘行為，不是實際聽感驗收。

官方依據：[音訊 renderer](https://developer.apple.com/documentation/avfoundation/avsamplebufferaudiorenderer)、[共同時間基準](https://developer.apple.com/documentation/avfoundation/avsamplebufferrendersynchronizer/timebase)、[設定時間與速率](https://developer.apple.com/documentation/avfoundation/avsamplebufferrendersynchronizer/setrate(_:time:))；並核對本機 visionOS SDK headers。

## 播放位置跳轉

時間列在拖曳結束時提交位置，另有前後 10 秒按鈕。位置限制於媒體範圍；前進至結尾直接停止並顯示結束，不對 EOF 建立解碼工作。暫停中跳轉先取得一張新位置畫面，再保持暫停，音訊不啟動；繼續後音畫共用新位置的時鐘。

`PlaybackController` 統一持有播放狀態。每次跳轉立即停止舊音訊、取消舊工作並更換 generation；等舊播放工作與 resource loader 尚未結束的讀取回呼完成清理才啟動最新要求。連續要求會淘汰中間位置，舊回呼不能更新畫面。取消仍受既有 SMB 單次 I/O timeout 限制，因此網路阻塞時新跳轉可能等待清理，不承諾即時定位。

每次跳轉重建 asset reader、硬解 session 與音訊 renderer。系統 reader 的 timeRange 指向目標，提供解碼順序的壓縮樣本與必要預解碼內容；第一個實際樣本必須不是 non-sync、partial-sync 或相依樣本，否則拒絕。預解碼限 30 秒、4,096 個樣本及 128 MiB 壓縮資料，不從頭掃完整影片作為備援。仍逐批核對 VideoToolbox 硬解屬性，沒有使用影像產生器或軟解影片。

目標前影格只供解碼參照，不顯示；通常顯示目標之後第一幀。若目標落在最後影格區間，保留解碼取得的末幀，顯示時間採所選位置。AAC／PCM reader 同步設定新時間範圍，音訊主時鐘從新位置開始；原有音訊限制不變。完整操作只以 H.264＋AAC 合成 MP4 驗證；MOV／M4V、VP9 的跳轉及 HEVC 的音訊／其他 profile 跳轉、多音軌、很長 GOP、缺失／不可靠索引、讀取中被修改檔案及真實 SMB 定位效能未驗收。缺少安全同步起點或超出預解碼界線會明確失敗。

`SyntheticSeek.mp4` 是測試套件內自造的六秒 H.264＋AAC 素材，含多個同步影格與 B-frame；產生器使用 `--seek`，影音交錯供給以避免 writer 輸入互等。不加入 app 示範資源，也不放入使用者分享。官方依據：[reader 時間範圍](https://developer.apple.com/documentation/avfoundation/avassetreader/timerange)；預解碼與 edit list 行為另以合成樣本驗證，不把 API 名稱當成跨格式保證。

## VR 投影呈現基礎

手動選擇等距柱狀 180° 或 360°，排列為單眼、左右或上下。左右排列預設左半給左眼、右半給右眼；上下排列預設上半給左眼、下半給右眼，可交換左右眼。需要切半的影像維度須為偶數，否則拒絕建立投影。這些選項不適用魚眼；自動設定只採下述明確容器標記，不依檔名或畫面猜測。手動格式可逐片保存，識別與失效規則見下節。

核心 `VRMesh` 建立朝內的球面／前半球網格，使用明確 UV 與法線；RealityKit ShaderGraphMaterial 的 camera-index switch 依眼睛選擇紋理。材質改編自 Apple 官方 MIT 範例，完整授權隨 app 打包，來源見授權與貢獻。單眼來源兩眼共用同一紋理；立體來源裁切已解碼影格，不增加影片解碼器。

`VRRenderer` 將既有 VideoFrame 的 CGImage 轉成紋理，最多保留處理中影格與最新待處理影格；過時設定或離開後的非同步結果不發布。這是可驗證的呈現原型，仍有 CPU 影格／GPU 紋理建立成本，沒有宣稱零拷貝、8K 效能、HDR 色彩正確性或實機流暢度。影片能進入 VR 前必須已有硬解影格，硬解政策不變。

沉浸空間保留暫停／繼續、每次 15° 的左右方向調整、方向歸零及返回視窗。進入時隱藏原視窗內容和系統覆層但保留其狀態，返回後恢復，不重建 SMB 登入。投影球半徑採固定 100 公尺，位置與方向採下述初始定位基準；初始定位與重新置中已加入，範圍見下節；方向歸零只清除手動角度，不重新讀取姿態。正常視線呈現由系統提供，未加入持續姿勢偵測或 ARKit 權限要求。

示範資料提供「投影測試圖」入口，會停止示範播放，且沉浸介面明示「投影測試圖，非影片播放」。自造格線圖只驗證幾何、材質與進出流程，不能用它替代硬解影片或實機雙眼立體驗收；普通 SMB 預覽不顯示此測試入口。

官方依據：[立體材質範例](https://developer.apple.com/documentation/visionos/displaying-a-stereoscopic-image-in-visionos)、[RealityKit 材質與紋理](https://developer.apple.com/documentation/realitykit/scene-content-materials-and-shaders)。初期仍需實機確認雙眼分派、上下方向、視角校準、沉浸控制位置及高解析度連續影片效能。


## 逐片 VR 格式保存

手動變更投影、立體排列或左右眼交換後，立即保存在 App 私有 Application Support；再次開啟同一影片時，先確認標頭，再套用設定。觀看方向不保存，每次從零開始。可繼續手動覆寫，或使用「清除此片格式」移除該片紀錄，重新採用容器辨識結果；沒有可靠標記時回到待手動選擇狀態。讀取檔案資訊期間暫停格式編輯，避免延遲恢復覆蓋新選擇；標頭讀取失敗時仍可手動設定，但不保存。

SMB 識別由登入時的主機、分享、帳號及分享內路徑組成，示範資料使用獨立命名空間。只正規化主機名稱的大小寫與首尾空白，其餘保留原值，以免錯誤合併不同檔案。IP 與主機別名視為不同來源；重新命名、移動或換帳號會視為新影片，不搜尋或追蹤舊路徑。App 不需要讀取密碼來識別影片。

沿用既有最多 64 KiB 標頭讀取，以檔案大小與標頭 SHA-256 作版本比對；不同時不套用舊紀錄。同大小且相同標頭、但後段內容改變的替換無法辨識，也不保證檢查後檔案不被修改。這不是全檔校驗、SMB 固定檔案 ID 或版本快照；不為設定掃描或下載整部影片。

保存內容只有格式、版本比對碼與以安裝本機隨機金鑰產生的 HMAC-SHA256 識別碼，不保存明文伺服器、帳號、分享、路徑、密碼或影片資料。隨機金鑰與設定同存 App 私有檔案，這是減少識別資訊，並非額外加密或防止已取得 App 容器的人分析；visionOS 檔案採 complete file protection，目錄排除備份，權限限制為目錄 0700、檔案 0600。解除安裝、清除 App 資料會失去設定；沒有跨裝置同步。

版本化 JSON 以原子寫入更新，MainActor 序列化操作，最多 5,000 筆、2 MiB；超限或寫入失敗明確提示，當次手動設定仍有效。損壞或未知版本不自動覆寫；舊路徑紀錄不自動清除，避免將暫時離線當成檔案刪除。本階段沒有全庫管理與搬移追蹤。


## 容器標記自動設定

`VRMetadataInspector` 解析 MP4 家族單一視訊軌道、單一視訊 sample description 中的 Spherical Video V2 `sv3d`／`st3d`。支援明確標示的完整等距柱狀 360°，或上下無裁切、左右各裁去四分之一的置中 180°；排列為單眼、上左下右、左左右右及右左排列，後者轉為左右排列並交換眼睛。依據為 [Google Spherical Video V2 規格](https://github.com/google/spatial-media/blob/master/docs/spherical-video-v2-rfc.md)。這是標記解析，不是檢查影片畫面是否真的符合標記。

目前只接受 avc1／avc3／hvc1／hev1／vp09 sample entry、單一視訊軌道、單一 sample description、零投影姿態及單位軌道變換矩陣；這些名稱不代表已驗證所有 codec 播放。投影與排列都須完整且唯一才能自動套用，缺任一項不推定單眼或 180°。重複／衝突、截斷、未知版本或超限皆回報需手動選擇；魚眼／mesh／cubemap、其他裁切或姿態、fragmented MP4、多視訊軌道、V1 XML、MKV／WebM 與其他 metadata 尚未支援。遇已知 V1 spherical UUID 與 V2 並存也不自動套用，以免忽略未解析的另一套標記。沒有檔名或長寬比猜測。

檢查最多 64 個頂層 box，以大小定位跳過 mdat；只載入最多 2 MiB 的 moov，分成不超過 64 KiB 的讀取，另加最多 1 KiB 頂層 header。moov 內最多 4,096 個 box，解析只走固定的軌道／sample entry 層級，檢查大小、溢位、父層邊界、短讀與取消；讀完再次核對檔案大小。超限不繼續掃描整部影片。這些界線只適用格式辨識，既有 AVFoundation 播放讀取策略不變；相同大小的讀取中修改仍不保證偵測。

已保存手動設定優先於容器結果；開始讀取格式後使用者做出的手動選擇也優先，不會被晚到的結果覆蓋。自動結果不落入手動保存紀錄。沒有可靠結果時顯示原因，可變更格式或按「使用目前格式」確認預設；未確認前不開啟影片 VR 投影，平面硬解播放仍可使用。示範投影圖為獨立測試入口，不代表影片已辨識或播放。清除手動覆寫後重新使用已取得的容器結果。

`tools/TagSyntheticMovie.py` 只對本專案自造灰階小檔加入 V2 360°／上下排列標記，產出 `SyntheticVR.mp4`，拒絕覆寫既有輸出；不進行解碼、轉碼或存取私人影片。「格式標記示範」使用這份素材，驗證的是容器與 UI，灰階畫面不代表實拍立體內容。影片解碼政策仍為強制硬解。


## 手動等距魚眼 180° 基礎

新增「等距魚眼 180°（置中圓）」手動模式。假設每眼為理想等距投影，總視角固定 180°，圓心在每眼影像中央、直徑等於短邊、影像頂部對應向上；先依單眼／左右／上下排列分眼，再套用該眼的圓形映射，亦可交換左右眼。這些參數固定且在介面明示，沒有自動猜測魚眼，也不依檔名或 V2 mesh 標記啟用。

球面方向相對前方的夾角 theta 對應圓心距離 r，採 r 與 theta 成正比；中心為正前方，90° 半視角對應圓周。UV 依分眼後的寬高比調整，矩形畫布中的圓不拉伸成橢圓；每眼尺寸或投影變更時重建網格。沿用朝內的前半球及既有硬解 CGImage 紋理路徑，不增加解碼器、轉碼或影片磁碟快取。模型區別可參考 [OpenCV 魚眼模型](https://docs.opencv.org/4.13.0/db/d58/group__calib3d__fisheye.html)；本原型不使用 OpenCV 程式庫，也不套用非零鏡頭畸變係數。

這個模式不涵蓋等立體角／正交／立體投影魚眼、偏心或裁切圓、其他視角、非方形像素、各廠牌鏡頭校正，以及前後雙魚眼的 360° 拼接。左右排列在此代表兩眼各自朝前的影像，不能拿前後兩鏡頭當左右眼。未提供鏡頭參數估計或視角／圓心／半徑調整，遇不符假設的素材不能宣稱已正確還原。

選擇會沿用逐片手動保存，優先於容器辨識；既有等距柱狀 180／360 UV 與 metadata 規則不變。新版本可讀取原有格式紀錄；不承諾舊版本降級後能讀取新增魚眼列舉值。

示範投影圖依排列產生自造魚眼校準圖，圓外黑色，上綠、右紅、下藍、左黃，30°／60°／90° 白色環線與方向軸。第一眼中心白色、第二眼中心洋紅，用來區別眼別；單眼刻意使用寬畫布，左右／上下則分眼為正方形，以覆蓋尺寸改變。此圖明示非影片播放，只用於映射與呈現驗證，不是實拍鏡頭素材，也不能證明實機雙眼效果或高解析度連續播放。


測試執行限制：目前核心／媒體驗收明確使用 `--no-parallel`。曾在大量媒體測試並行時停滯，採樣顯示多個 AVAssetReader 同步取樣等待；序列執行通過，尚未修正或證明併發解碼／讀取排程完全安全。這不等同於魚眼映射失敗，也不能由序列通過推論多播放器並行可靠，詳見本輪驗收。


## 影片初始視角與手動重新置中

使用公開 `WorldTrackingProvider.queryDeviceAnchor(atTimestamp:)` 取得裝置相對 App 原點的姿態。Apple 說明裝置姿態查詢只在沉浸空間可用，且不需要授權；因此本原型在每支影片第一次進入 VR 時取得基準，不在檔案瀏覽或平面預覽時假稱已取得方向。參考 [Apple 頭部／裝置定位範例](https://developer.apple.com/documentation/visionos/placing-entities-using-head-and-device-transform) 與 [裝置姿態 API](https://developer.apple.com/documentation/arkit/worldtrackingprovider/querydeviceanchor(attimestamp:))。使用公開 API 不等同已完成 App Store 審查。授權範圍另依 [Apple ARKit 存取說明](https://developer.apple.com/documentation/visionos/setting-up-access-to-arkit-data/) 核對 world tracking 與 world sensing 的區別。

`DeviceInitialPose` 先檢查支援狀態與所需授權清單；若平台要求額外授權便不啟動，也不呼叫授權請求。只啟動 world tracking provider，不加入世界錨點、手部、平面、網格或相機資料 provider。啟動後最多以 50 ms 間隔嘗試 40 次，另有 3 秒 watchdog 停止 session；第一個 tracked 且有效的姿態取得後立即停止，取消或錯誤也停止。這是初始定位的短暫取得，不是播放期間逐幀查詢或持續校準；native session 停止完成時間仍受系統影響。

基準保留完整平移及旋轉，不把俯仰或側傾削成世界水平，讓仰躺／側躺也可依當下方向觀看。純計算驗證姿態為有限、近似正交且右手系的剛體矩陣；無效資料不以 identity 假裝成功。裝置位置與頭部中心並非完全相同，實機差異仍待確認。

同一影片離開再進入 VR 不重新取姿態；新影片清除基準。「重新置中」是明確的手動再取一次，成功後歸零手動角度，失敗保留先前視角並提示。手動左右、上下及左右傾斜以初始局部座標每次 15° 調整；「方向歸零」只清除這些偏移。只有校準尚在取得時暫停方向按鈕，返回仍可使用。基準未取得時使用明示降級的預設位置，保留手動操作。

控制框優先放在已取得的固定基準下，基準不可用時使用系統 `AnchorEntity(.head)` 的 `.once` 模式作為控制框備援；不讀取該錨點被隱藏的 transform，也不持續讓控制框跟隨頭部。重新置中與系統數位旋鈕重新置中的座標行為不同：本原型沒有保存世界錨點，系統變更 App 原點仍可能移動內容，不能宣稱跨場景原點或實際房間位置永遠固定。

姿態只留在記憶體，不寫入日誌、逐片格式、專案或雲端；逐片保存仍只有投影／排列／交換眼睛。新影片及 App 重啟不沿用舊姿態。未新增世界感知、手部或相機用途說明／權限，既有 SMB 本機網路用途說明維持；實機坐躺、拒絕／失去追蹤與系統原點變更仍需另行驗收。


本功能的姿態處理不傳出裝置；依 [Apple App Privacy 說明](https://developer.apple.com/app-store/app-privacy-details/)，完全在裝置上處理的資料與傳出裝置的資料收集須分開判斷。這不是整個 App 或第三方依賴的上架隱私審查結論，正式發布仍須以當時完整資料流核對。

| --- | --- | --- |
| MP4／H.264 | 原生解封裝、強制硬解；自造 64×64 影片在 Mac 完成播放、AAC 同步及多 GOP 跳轉回歸 | 實機、高解析度及其他 profile |
| MP4／HEVC | 原生解封裝、強制硬解；自造 64×64、12 fps、2 秒無音軌 B 影格樣本，在 Mac 從頭及 1 秒定位成功 | Main10／HDR、多 GOP、音訊組合、高解析度與實機 |
| MP4／VP9 | 存在 codec 辨識與強制硬解分支 | 合成 VP9 MP4 在本次 Mac 可辨識軌道但硬解不可用；實機未驗證，不列為已驗證相容 |
| MKV／上述任一編碼 | 尚未實作解封裝，讀取來源前即拒絕 | 不因底層 codec 可硬解就推定 MKV 可播放 |
| MOV／M4V | 允許進入系統解析管線 | 尚無獨立容器樣本驗收，改副檔名不構成驗證 |

HEVC 測試揭露 B 影格的 PTS 可早於 DTS，原本以 DTS 釋出影格會過早顯示。現在 HEVC 保留最多 16 幀的排序視窗，結尾排空；超出視窗而出現倒退仍停止，不跳過錯誤影格。沿用 32 幀／128 MiB 總佇列上限，且不啟用可選的 decoder temporal processing；官方旗標說明見 [Apple VideoToolbox](https://developer.apple.com/documentation/videotoolbox/vtdecodeframeflags/kvtdecodeframe_enabletemporalprocessing)。這會增加起播預讀與影格記憶體需求，高解析度可能先觸及上限，尚未宣稱適合 8K 或網路效能。H.264 既有排序保持原邏輯，其他 codec 不推定已解決。

未知 codec 現在明示「這個視訊編碼尚未支援，已停止播放。」；軌道不合法與硬解不可確認維持各自錯誤。所有實際影格仍必須通過 require-hardware session 與實際硬解屬性檢查，未增加軟解、轉碼或第三方依賴。

自造素材工具新增 `--hevc`，使用 [Apple HEVC codec](https://developer.apple.com/documentation/avfoundation/avvideocodectype/hevc) 與 AVAssetWriter 直接編碼程式生成的灰階像素；不是讀取或轉碼使用者影片。`SyntheticHEVC.mp4` 只供測試，不加入 App 示範資料。VP9 與 MKV 仍需另行挑選合規來源／解封裝方案，這輪未安裝程式庫。


MKV 解封裝候選、libwebm 隔離原型、授權與 VP9 平台探測統一見 [MKV 與 VP9 評估](MKV與VP9評估.md)；App 尚未加入 MKV 依賴或入口。


預定 MKV 的新 SMB session 契約已加入編譯與測試，但未替換既有播放器來源；共享名額、draining 與版本能力分級見 [SMB 讀取生命週期](SMB讀取生命週期.md)。現有 adapter 無不可變快照承諾，預設安全拒絕，不能視為 MKV 已支援。

## 2026-11-04 捷徑瀏覽入口

以 `VistaBrowser.xcodeproj`／`VistaBrowser` scheme 建置；原播放器專案仍保留。功能、快取、憑證與測試限制見 [捷徑瀏覽](捷徑瀏覽.md)，回歸來源為 `VistaUITests/BrowserUITests.swift` 及新增核心測試。兩入口不混用 UI suite。

## 2026-11-04 播放銜接

新瀏覽選片接入共用 PlaybackView／VRImmersiveView；正式規格及限制見 [播放整合](播放整合.md)。模擬器試用明確使用 `SWIFT_ACTIVE_COMPILATION_CONDITIONS="DEBUG VISTA_SIMULATOR_SOFTWARE_DECODE"`，正常 Debug／Release 不預設此旗標；合成片在「本機（示範）」→「播放測試」。不需要登入 SMB，也不要用真實網路成功取代影片／實機驗收。
