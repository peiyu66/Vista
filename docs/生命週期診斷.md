# 生命週期與 SMB 匿名診斷

2026-11-07。正式整合保留 Build64 使用的 schema 4 本機匿名時間線及同步關鍵副本，協助區分 UI、Task、provider、SMB 回呼與恢復步驟。本文件是現行診斷的正式來源；診斷不是退出或播放黑畫面的修復證據。SMB 行為見 [SMB 目錄恢復](SMB目錄恢復.md)，來源與測試狀態見 [已驗收基底](已驗收基底.md)。

## 記錄內容與隱私

`LifecycleDiagnostics` 在 app 私有 Application Support 的 `VistaLifecycleDiagnostics` 目錄寫入 JSON Lines，不上傳。內容只接受固定 enum、數字、版本、時間、程序識別與隨機執行識別；session／navigation／request 是該次程序內的遞增編號，不由來源、路徑或帳號衍生。

不記錄檔名、伺服器、分享、URL、session key、來源 UUID、帳號、帳密、原始 Error／userInfo／錯誤文字。公開摘要不包含實際裝置識別、程序與執行識別值、私人路徑或原始日誌。

## 事件順序與解讀

1. `browseIntent` → `cancelRequested` → `requestStart`：UI 意圖、取消要求及新請求。requestStart 仍在 Task 建立前，不代表工作本體已執行。
2. `taskCreated` → `taskEntered` → `taskExited`：Task 已建立、本體開始及 defer 到達；scope 1 為目前目錄，2 為父目錄。Exited 不證明子工作或 library 排空。
3. `sessionLookup` → `sessionReused` 或 `sessionCreateRequested`：查找與選擇 session。Reused 不保證仍有效；CreateRequested 位於憑證讀取前，不是已讀憑證或連線完成。
4. `providerWillCall` → `providerEntered` → `providerExited`：呼叫前、進入及離開 provider；離開也可能是 throw，不能單獨當成成功。
5. page 的 `cacheMiss` 或 `cacheHit`：Miss 才走真正 contentsOfDirectory；Hit 不虛構 SMB 呼叫。
6. `apiStart` → `apiReturned` 或 `apiError`：真正 manager 呼叫前與 completion 邊界。成功回呼之後仍須 `directoryMappingDone`、provider 返回及 UI 處理。
7. `resultApplied`／`resultDiscarded`／`requestError`：UI 套用、取消／過期丟棄或錯誤。回呼成功不等於 UI 已顯示。

API 事件的 request 是 API 編號，parentRequest 才連回 UI request；provider／cache／session 事件的 request 直接是 UI 編號。operation 固定為 connect=1、listShares=2、listDirectory=3、attributes=4、rangeRead=5、tagRead=6、finderInfo=7、disconnect=8。不能把正常標籤不存在誤讀成列目錄失敗。

`recoveryStage` 的 phase 為 1 開始、2 舊 provider 退役、3 新連線完成、4 重列成功、5 失敗、6 過期丟棄。`errorOrigin` 為 0 未分類、1 serviceInvalidated、2 submission、3 response、4 wait、5 contextUnavailable。service 通用 -1 不冒充 POSIX EPERM；只有邊界有定義時才保存 POSIX 數字碼，不從可變 context 的舊錯誤推測。

`scenePhase` 的 scope 0 為 App 聚合、1 Browser、2 Immersive；phase 0 active、1 inactive、2 background。它們是系統／視窗狀態，不是摘戴感測器。`viewAppear`／`viewDisappear` 也不等於程序開始／終止。`readerClosed.active` 僅涵蓋該 media reader 的讀取，不代表全部 RPC 或遠端 handle。

正式來源仍只在 background 執行原暫停策略；inactive 僅被觀測，不提早暫停。沒有 renderer 恢復、訊號 handler、背景延時、連線保活或自動重播。

## 同步關鍵副本

一般 `current.jsonl` 與 `previous-1...3.jsonl` 仍為非同步完整時間線；`critical-current.jsonl` 與 `critical-previous-1...3.jsonl` 為關鍵事件副本。關鍵 record 先捕捉時間與序號並排入一般時間線，再於函式返回前等待獨立 serial writer 完成 append 與 FileHandle.synchronize，或捕捉失敗。不等待一般 writer 排空，也不持有其 admission lock 等檔案。

同步範圍限程序開始、scenePhase、browse／取消／UI request、Task、session 選擇、cache、mapping／UI 結果、recoveryStage，及 connect／listShares／listDirectory 的 provider／API 邊界。rangeRead、tagRead、finderInfo、attributes 不因錯誤或 priority=true 全部變成同步；沒有新增逐幀或逐檔同步寫入。

contentsOfDirectory completion 在 mapping／continuation.resume 前先記成功或失敗邊界。同步診斷增加等待並改變執行時序；API durationMS 包含開始事件的診斷成本，不是純 SMB RPC 時間。

寫入、輪替或 synchronize 失敗只累計 `syncFailures`，不向應用邏輯拋錯或循環重試。`syncWrites` 為成功完成同步寫入數；`syncSlowWrites` 計至少 50 ms 的等待，`syncMaxDurationMS` 記最長等待。各 record 只帶捕捉前已知的累計值，不能用該筆的 counter 證明它自己已持久化；無後續事件時最新失敗也可能只留在記憶體。

50 ms 是觀測門檻，不是 timeout。磁碟、系統或前序關鍵寫入停滯沒有硬耗時上限，MainActor 或 SMB 回呼也可能等候，過長可增加 watchdog 風險。同步返回能減少尾端遺失，卻不保證 crash、強制終止或斷電前最後一筆一定保存。OSLog 是另一份系統證據，不由本機檔案寫入結果推定其保存狀態。

## 容量與讀取

一般 writer 最多 128 筆 pending、每檔 256 KiB × 4；關鍵副本每檔 64 KiB × 4，兩組內容合計約 1.25 MiB，不含檔案系統 metadata。pending 限制不等於所有同時等待呼叫者的總記憶體上限。啟動時按修改時間清理超過七日的檔案；不是每筆記錄七日硬期限。目錄／檔案權限為 0700／0600、排除備份，裝置檔案使用 completeUntilFirstUserAuthentication。

rangeRead／tagRead／finderInfo 各每秒最多抽一組開始／結束；一般 metadata 缺失／拒絕不逐筆升為 notice。其他錯誤可保留 sampledStart=0。dropped、omitted、writerFailures 由後續寫出的事件帶上，沒有事件不能推定計數為零。

分析兩組檔案時按執行識別與 sequence 去重、排序，再對照 request／navigation／operation 與程序生命週期。兩組是同一 record 的副本，不能算成兩次操作；實際落筆順序未必等於捕捉序號。任意位置的不完整或不合法行都須統計並略過。部分寫入失敗後重新開檔會核對長度，缺 newline 時補分隔，並不修復損毀內容。schema 4 可讀較早 optional 欄位，舊 reader 不保證理解新事件。

## 驗證及證據限制

本機測試涵蓋固定欄位、錯誤分類、TaskLocal 關聯、配對抽樣、容量／輪替／權限、失敗不外拋、無 drain 可見關鍵副本、延遲注入、部分寫入與舊 schema。替身／檔案測試不能代表所有實機交錯或突死寫入；正式重驗結果統一見 [已驗收基底](已驗收基底.md)。

Build64 實測確認的 4 次新連線／重列／UI 套用摘要見 [SMB 目錄恢復](SMB目錄恢復.md#實測證據與停止界線)。未取得與另一次回 Home 事件匹配的 crash／終止證據，依使用者指示停止追查。缺少事件不證明 crash、死鎖、SIGPIPE 或任何特定原因；此結案不新增持續收集或實機操作授權。

若日後另有授權調查，系統 crash／Jetsam 證據應先匹配版本、時間與 binary UUID，不能沿用舊報告替代。參考 [Apple crash 與裝置日誌](https://developer.apple.com/documentation/xcode/diagnosing-issues-using-crash-reports-and-device-logs)、[取得診斷紀錄](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs)、[Jetsam](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports)。
