# 保留解碼狀態向前恢復 206

使用者完成 206 實機測試，回報明顯改善並要求先提交再檢討日誌。正式整合基於 `d9018e14`，來源建置使用 207，以區分已測的實驗二進位。這次不發布商店或操作實體裝置。

## 行為與範圍

自動視訊降速確認新倍率後，仍沿用 194 的直接恢復資格及來源、命令、暫停檢查。對符合資格的 2–3× HEVC 單視訊／單音訊播放，先凍結共同時鐘、確認兩個輸出已暫停，保留 decoder 參考鏈及既有 PCM。視訊 FIFO 缺少輸入時繼續 demux 供應，已過期輸出正常丟棄；取得目標影格後恢復原輸出、共同時鐘及 timer。沒有跳回關鍵影格或 codec flush。

不再限定每個來源只能 hold 一次，也不要求開始前 FIFO 至少兩筆。明確控制取消、來源真正耗盡、格式／decoder 結束走既有狀態處理；不增加假設性超時。沿用經 188/189 實際問題修正的恢復後首張與持續進展檢查及一次 seek fallback，未把原始的凍結回歸當成改善證據。

204 的三筆在途、無 100 ms 旁通及有限非參考 preroll 省略保持。正式基線原本沒有 hold，這次包含必要的 hold／timer／取消基礎；排除音訊儲備192、195 呈現清理、197 來源記錄器及額外實驗日誌。Release／Diagnostic 使用同一恢復策略；Diagnostic 日誌格式暫不重設。

## 核驗

原生 input 與實測206逐字相同，es_out 僅排除 seek-phase 診斷，request／decoder／橋接關鍵函式相同；原庫 player/timer object 相同。對應來源與核驗摘要見 `tools/Recovery206/baseline.json`。

- `python3 tools/Recovery206/test_forward.py`：128 項實際 coordinator／decoder helper 檢查，含暫停確認、需求供應、source buffering、EOF、取消與 reference lifetime；ASan/UBSan 及另行 TSan。
- `python3 tools/Recovery206/test_clocks.py`：210 項共同時鐘／input PCR／timer 檢查，最佳化與 ASan/UBSan。
- `python3 tools/Recovery206/test_pcm.py`：631 項實際 render/pause 函式檢查，涵蓋 63 種區塊內位置；最佳化與 ASan/UBSan。
- `python3 tools/Recovery206/verify_policy.py`：既有直接恢復 255 項、恢復後進展 41 項，分別未最佳化及最佳化執行。
- `python3 tools/Recovery204/verify.py`：原三筆 admission、回呼／取消及 metadata/pacer 回歸；最佳化、ASan/UBSan、TSan。
- 35 個 overlay 單元重新編譯、當前 MKV producer 重新編譯，Release／Diagnostic 完整建置；日誌與 lifecycle 回歸另核對。

這些主機測試使用可識別的合成 PCM、模擬 FIFO／裝置 sink，不等於實體 AudioUnit 或螢幕音畫量測。底層未修改依賴沿用已核實的基底庫，未聲稱整套依賴重新建置。

## 已有實機證據與界線

206 四次完成向前恢復，保持 decoder 世代，沒有觀察到重解先前已完成的壓縮輸入；決策至首張交付約 942、1038、596、1000 ms。另一決策被後續降速取代，不能當成獨立成功。樣本與 204 的片段、工作量不同，不是嚴格 A/B，總恢復仍可能超過一秒。

恢復後 timer 與畫面持續前進，未見該窗口 VT 錯誤；不宣稱量測到物理音畫同步或所有長時間情境。正式整合 207 尚未安裝，使用者驗收的是 206。上架 Release 是否建立自製日誌，需另以實際執行及乾淨容器核對，建置成功不算執行證據。
